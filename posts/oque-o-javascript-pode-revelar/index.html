O que o JavaScript pode revelar


Introdução

Durante meus estudos de segurança em aplicações web, uma das coisas que mais chamou minha atenção foi entender como aplicações modernas funcionam internamente e como pequenos detalhes de implementação podem revelar problemas de segurança.

Para praticar os conhecimentos que vinha adquirindo, decidi analisar uma aplicação real sob uma perspectiva de segurança.

Meu objetivo não era apenas encontrar vulnerabilidades, mas entender como a aplicação era construída, como seus componentes se comunicavam e como os controles de segurança eram implementados.



Explorando a Aplicação

Comecei explorando a aplicação e tentando entender sua estrutura.

Analisei requisições, observei como diferentes funcionalidades se comunicavam com o backend e identifiquei as tecnologias utilizadas.

Durante essa análise, percebi que a aplicação utilizava Angular como framework no frontend.

Como frameworks modernos frequentemente carregam informações importantes sobre rotas, funções internas e comunicação com APIs, decidi analisar os arquivos JavaScript carregados pelo navegador.



Seguindo os Rastros do JavaScript

Enquanto revisava o código JavaScript, comecei a procurar por funções interessantes, rotas expostas e possíveis fluxos ocultos da aplicação.

Durante essa análise, encontrei uma função chamada:

createUser()

O nome da função chamou minha atenção, pois sugeria uma funcionalidade relacionada ao gerenciamento de usuários.

Ao acompanhar seu funcionamento, encontrei uma chamada para o endpoint:

/new/edit

Nesse momento, quis entender se aquilo era apenas uma referência interna do frontend ou se o endpoint realmente estava acessível.

Então, adicionei manualmente /new/edit à URL da aplicação e acessei a rota diretamente.

De forma inesperada, a aplicação carregou uma página de criação de usuários.



A Descoberta

A página permitia criar um novo usuário e preencher informações como e-mail, nome, telefone e o cargo do usuário.

O que chamou minha atenção foi que minha conta atual não deveria possuir acesso a essa funcionalidade.

A interface da aplicação não apresentava essa opção para o meu usuário, porém, ao acessar a rota diretamente, eu conseguia chegar até a página.

Nesse momento, percebi que a restrição existia apenas no frontend.

A aplicação escondia a funcionalidade dos usuários, mas o backend não realizava corretamente a validação de autorização antes de permitir a execução da ação.

Foi então que confirmei que havia encontrado uma vulnerabilidade de Broken Access Control.



Reportando o Problema

Após confirmar o comportamento e criar uma Prova de Conceito, demonstrando o problema, reportei a vulnerabilidade para a equipe responsável.

O problema foi analisado e posteriormente corrigido.



Lições Aprendidas

Essa experiência reforçou a importância de analisar aplicações além do que está visível através da interface do usuário.

Aplicações web modernas possuem diversas camadas, e o frontend pode revelar informações valiosas sobre rotas, lógica interna e possíveis superfícies de ataque.

Porém, a principal lição foi entender que segurança nunca deve depender apenas de esconder funcionalidades dos usuários.

Uma funcionalidade que não está visível não significa que ela está protegida. Os controles de autorização devem sempre ser aplicados no backend, onde a ação realmente é processada.
